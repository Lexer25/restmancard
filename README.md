# Модуль restmancard — организации и сотрудники из REST API v2

Версия 1.7.0 (22.11.2026)

Модуль повторяет трёхпанельную форму `mancard/index`, но основные данные берёт
из Artonit REST API v2 (из Firebird читается только карта привязки сотрудников
`TABNUM -> ID_ORG`, см. раздел «Сотрудники в ветках организаций»):

* Swagger-контракт: <http://localhost:5056/swagger/v2/swagger.json>
* Страница модуля: `https://localhost/city/index.php/restmancard/index`

## Сотрудники в ветках организаций

С версии 1.6.0 сотрудник показывается в ветке **своей** организации. При клике
по строке организации ветка раскрывается: видны дочерние организации и
сотрудники этой организации. Свернуть ветку можно кнопкой-стрелкой (📁/📂),
кнопки «Развернуть всё» / «Свернуть всё» и поиск работают как раньше.

Порядок в ветке: сначала дочерние организации (по названию), затем сотрудники
(по ФИО, затем по `tabnum`). Бейдж 👤 у организации — число её сотрудников;
в панели «Свойства» поле «Сотрудников» показывает это число, а «с вложенными» —
сумму по всем подчинённым подразделениям.

### Контракт привязки

| Источник | Поле | Назначение |
|---|---|---|
| `GET /api/v2/Person/GetList` | `tabnum` | ключ сотрудника |
| Firebird `PEOPLE` | `TABNUM`, `ID_ORG`, `ID_DB` | организация сотрудника |
| `GET /api/v2/organizations` | `id` | `ID_ORG` организации в дереве |

REST API v2 не сообщает организацию сотрудника: в ответе
`GET /api/v2/Person/GetList` есть только `tabnum`, `surname`, `name` и
`patronymic`, а недокументированные фильтры (`id_org`, `org`, `organization`)
сервис игнорирует. Поэтому модуль читает из Firebird **только карту
`TABNUM -> ID_ORG`** — из той же базы, с которой работает REST-сервис;
остальные данные по-прежнему приходят из REST API.

Запрос карты (`Model_Restmancard_People::fetchOrganizationMap()`):

```sql
SELECT p.TABNUM, p.ID_ORG
FROM PEOPLE p
WHERE p.ID_ORG > 0
  AND p.ID_DB = 1
ORDER BY p.ID_ORG
```

`ID_DB` задаётся настройкой `people.org_map_id_db`, фильтр по активности —
`people.org_map_active_only` (по умолчанию `false`: в дереве показываются все
сотрудники, как и раньше). Строки `TABNUM` перекодируются из windows-1251 в
UTF-8, сравнение с REST-списком идёт сначала точно, затем без учёта регистра.
Карта кешируется на `people.org_map_cache_lifetime` секунд в ключе
`restmancard_people_org`; кнопка «Обновить» (`?refresh=1`) и операции с
сотрудниками сбрасывают её.

### Если привязка недоступна

* `people.org_map = false` — Firebird не используется, все сотрудники
  показываются у организации `people_root_divcode` (поведение версий 1.0–1.5);
* инстанс БД недоступен или запрос завершился ошибкой — выводится
  предупреждение, сотрудники также показываются у `people_root_divcode`;
* в подвале панели «Организации» выводится число сотрудников без привязки,
  в панели «Свойства» — пояснение, почему они собраны в этой организации.

Сотрудник без `ID_ORG` (или с `ID_ORG`, которого нет в списке REST) попадает
в организацию `people_root_divcode`. Такие сотрудники не теряются: счётчик
«Сотрудников» в подвале показывает общее число.

## Добавление организации

Кнопка «Добавить» в заголовке панели «Организации» открывает модальное окно
(название, `divcode`, родительская организация, флаг). Форма отправляет AJAX
запрос на `restmancard/add_organization`, контроллер проверяет поля по
контракту и вызывает `POST /api/v2/organizations`. После успешного создания
кеш списка организаций сбрасывается, страница перезагружается с `?refresh=1`,
и новая организация появляется в дереве.

Если перед открытием окна в дереве выбрана организация, она подставляется как
родительская; вариант «— Корневая организация —» создаёт корень.

### Чекбокс «Автоматически» у поля divcode

Под полем «Код организации (divcode)» есть чекбокс **«Автоматически»**
(включён по умолчанию):

* **включён** — поле `divcode` заблокировано, подсказка меняется на «Код будет
  сформирован из названия организации. Префикс: `dv_`». В AJAX уходит
  `divcode_auto=1` и пустой `divcode`;
* **выключен** — поле доступно для ручного ввода; если код введён, он
  проверяется на 1–50 символов из набора `A-Z a-z 0-9 . _ -` и на занятость.
  В AJAX уходит `divcode_auto=0` и введённый код;
* если поле `divcode` **пустое при любом положении чекбокса**, сервер
  сформирует код автоматически (требование: «если пользователь не указал
  divcode, сформировать его автоматически»). Поэтому обязательной звёздочки у
  поля нет.

После создания сервер возвращает `divcode` в JSON-ответе, поэтому страница
перезагружается с `?refresh=1&focus=<сформированный код>` и раскрывает ветку
именно новой организации. Сообщение об успехе показывает сформированный код:
«Организация добавлена. Код сформирован автоматически: `dv_otdel_prodazh`».

Контракт AJAX-запроса `restmancard/add_organization` (POST, form-data):

| Поле | Обязательное | Назначение |
|---|---|---|
| `name` | да | название организации, 1–50 символов |
| `divcode_auto` | нет | `1` — сформировать код автоматически, `0` — взять из `divcode` |
| `divcode` | нет | ручной код; пусто — код будет сформирован автоматически |
| `parent` | нет | `divcode` родителя; пусто — корневая организация |
| `flag` | нет | `0` — обычная, `1` — гостевая |

### Как формируется divcode

`Model_Restmancard_Org::generateDivcode()`:

1. Название транслитерируется в латиницу (`Отдел продаж` → `otdel_prodazh`);
   карта транслитерации встроена в модель (`$_translit`), поддержаны русские и
   украинские буквы, `ё`, `ъ`, `ь`. Нижний регистр, недопустимые символы
   заменяются на `_`, повторы `_` и разделители по краям убираются.
2. Добавляется префикс из настройки `organizations.divcode_prefix`
   (по умолчанию `dv_` — как у `dv_All`/`dv_Guest`): `dv_otdel_prodazh`.
3. Код проверяется на занятость по **всем** загруженным организациям
   (сравнение без учёта регистра). Если код занят, добавляется номерной суффикс
   `_2`, `_3`, … (`dv_otdel_prodazh_2`), не более
   `organizations.divcode_max_attempts` попыток. После исчерпания — короткий
   случайный хвост.
4. Длина ограничена 50 символами (контракт API): длинная часть названия
   обрезается с сохранением суффикса.
5. Если название не даёт ни одного допустимого символа (`###`), берётся
   `dv_org`.

Так как список организаций кешируется на `cache_lifetime` секунд, код,
занятый в базе, но ещё не попавший в кеш, может вызвать ответ API `409
Conflict`. В этом случае `createOrganization()` формирует следующий свободный
код и повторяет `POST` — не более `organizations.divcode_retry_on_conflict`
раз. Для ручного кода `409` сразу возвращается пользователю.

## Удаление организации

Кнопка «Удалить» в заголовке панели «Организации» активна, когда в дереве
выбрана организация; при выборе сотрудника она заблокирована. Нажатие открывает
окно подтверждения с названием и `divcode`. Если по данным дерева у организации
есть подразделения или сотрудники, окно предупреждает об этом — окончательное
решение всё равно принимает API.

Подтверждение отправляет AJAX-запрос `restmancard/delete_organization` (POST,
form-data), контроллер вызывает `DELETE /api/v2/organizations/{divcode}`. После
ответа `204 No Content` кеш списка организаций сбрасывается, страница
перезагружается с `?refresh=1`, а ветка родительской организации раскрывается.

| Поле | Обязательное | Назначение |
|---|---|---|
| `divcode` | да | код удаляемой организации |

REST API v2 удаляет только пустую организацию. Если у неё есть дочерние
подразделения или активные сотрудники, сервис возвращает `409 Conflict` с телом
`OrganizationDeleteConflict` (`error`, `message`, `childrenCount`, `children`,
`peopleCount`, `people`). Контроллер превращает этот ответ в понятное сообщение,
например:

> Нельзя удалить организацию: у неё есть дочерние организации (3).
> Сначала удалите или переместите дочерние организации.

Ответы `404` (организация уже удалена) и `403` (нет прав) также показываются в
окне. Удаление некаскадное: сотрудники и подразделения должны быть удалены или
перемещены заранее.

## Добавление сотрудника

Сотрудник добавляется в **выбранную организацию**. Открыть окно можно двумя
способами:

* кнопка с иконкой сотрудника в заголовке панели «Организации» — организация
  по умолчанию берётся из выделения в дереве (если выделен сотрудник — его
  организация, если ничего не выделено — `organizations.people_root_divcode`);
* кнопка «Добавить сотрудника» в панели «Свойства» выбранной организации.

В окне есть выбор организации (список всех организаций с путём в дереве),
фамилия, имя, отчество и табельный номер. Обязательна только **фамилия**.

### Чекбокс «Автоматически» у поля tabnum

По умолчанию чекбокс снят, и поле `tabnum` доступно для ввода — номер можно
предложить вручную.

* **снят** — если номер введён, он передаётся в `POST /api/v2/Person`;
  проверяется длина (1–50 символов) и занятость (сравнение без учёта регистра).
  Если поле пустое, номер формируется автоматически;
* **установлен** — поле блокируется, в AJAX уходит `tabnum_auto=1` и пустой
  `tabnum`. Сервер не передаёт `tabnum` в API, и сервис формирует номер сам
  как `tn_<ID сотрудника>` (это описано в swagger: «Если tabnum не указан,
  он формируется как tn_<id_pep>»). Сформированный номер возвращается в ответе
  `POST` и показывается в сообщении об успехе.

Подсказка под полем меняется так же, как у `divcode`: «1–50 символов. Пустое
поле — номер будет сформирован автоматически (tn_<ID>)» либо «Номер сформирует
REST API автоматически: tn_<ID сотрудника>».

### Как создаётся сотрудник

`Model_Restmancard_People::createPersonWithOrganization()`:

1. `POST /api/v2/Person` с `surname`, `name`, `patronymic` и, для ручного номера,
   `tabnum`. Организация в этом запросе **не передаётся** по контракту API:
   сервис создаёт сотрудника с `ID_ORG = 1`.
2. `PATCH /api/v2/Person` с `tabnum` и `id_org` выбранной организации —
   привязка к организации. `id_org` берётся из списка организаций по её `id`
   (поле `ID_ORG`), а не из произвольного числа, присланного браузером.
3. Если `PATCH` не удался, только что созданный сотрудник удаляется
   (`DELETE /api/v2/Person`), чтобы в API не осталось записи без организации.
   В ответе будет текст ошибки привязки и пометка, удалось ли откатить создание.

Контракт AJAX-запроса `restmancard/add_person` (POST, form-data):

| Поле | Обязательное | Назначение |
|---|---|---|
| `id_org` | да | `ID_ORG` организации из списка дерева |
| `surname` | да | фамилия, 1–50 символов |
| `name` | нет | имя, до 50 символов |
| `patronymic` | нет | отчество, до 50 символов |
| `tabnum` | нет | табельный номер, до 50 символов; пусто — сформировать автоматически |
| `tabnum_auto` | нет | `1` — сформировать номер автоматически, `0` — взять из `tabnum` |

Ответ при успехе:

```json
{
  "success": true,
  "message": "Сотрудник добавлен. Табельный номер сформирован автоматически: tn_245",
  "tabnum": "tn_245",
  "tabnum_generated": true,
  "full_name": "Иванов Иван Иванович",
  "organization": {"id": 66, "divcode": "dv_testovaya_organizaciya_1", "name": "Тестовая организация 1"}
}
```

Ошибки:

* `surname` пустая или длиннее 50 символов, `name`/`patronymic` длиннее
  50, `tabnum` длиннее 50 — ответ `success: false` с `errors` по полям,
  форма подсвечивает поля;
* ручной `tabnum` уже занят — та же проверка до запроса в API; если сотрудника
  успели создать параллельно, API вернёт `409`, и ответ тоже укажет на поле
  `tabnum`: «Сотрудник с таким табельным номером уже существует»;
* `400` от API — показывается сообщение сервиса;
* `403` — «Недостаточно прав для добавления сотрудника»;
* организация не выбрана или её нет в загруженном списке — ошибка `id_org`.

После успеха страница перезагружается с
`?refresh=1&focus=<divcode>&person=<tabnum>`: кеш сбрасывается, ветка
организации раскрывается, новый сотрудник выделяется в дереве и в панели
«Свойства». Если организация не отображается в дереве (например, выключена
привязка `people.org_map`), сотрудник всё равно создан и привязан в API.

## Удаление сотрудника

Кнопка «Удалить» в заголовке панели «Организации» активна, когда в дереве
выбран сотрудник **или** организация, и удаляет именно выбранный элемент.
Содержимое окна подтверждения зависит от типа:

* организация — название, `divcode`, предупреждение о дочерних организациях и
  сотрудниках (см. раздел «Удаление организации»);
* сотрудник — ФИО, `tabnum` и организация, предупреждение о том, что вместе с
  сотрудником API удаляет его идентификаторы (карты).

Удаление сотрудника также доступно кнопкой «Удалить сотрудника» в панели
«Свойства» выбранного сотрудника.

Подтверждение отправляет AJAX-запрос `restmancard/delete_person` (POST,
form-data), контроллер вызывает `DELETE /api/v2/Person?tabnum=...`.

| Поле | Обязательное | Назначение |
|---|---|---|
| `tabnum` | да | табельный номер удаляемого сотрудника |

Ответы и ошибки:

* `200` — «Сотрудник удалён»; кеш сотрудников, идентификаторов и карты
  `TABNUM -> ID_ORG` сбрасывается, страница перезагружается с `?refresh=1` и
  раскрывает ветку организации удалённого сотрудника;
* `404` — «Сотрудник не найден — возможно, он уже удалён. Обновите страницу»;
* `409` — показывается сообщение API (например, если сотрудник используется в
  других данных сервиса);
* `403` — «Недостаточно прав для удаления сотрудника»;
* пустой `tabnum` — «Не выбран сотрудник для удаления».

Вместе с сотрудником API удаляет его идентификаторы (карты). Других
зависимостей модуль не проверяет: если сервис запретит удаление, вернётся `409`
и его сообщение будет показано в окне.

## Тестовые организации (задача `restmancard:seed`)

Для наполнения дерева тестовыми данными в модуле есть Minion-задача: она
создаёт в корне 5 организаций и по 3 дочерних подразделения в каждой.

Запуск из командной строки Windows:

```
c:\xampp\php\php.exe c:\xampp\htdocs\city\modules\minion\minion --task=restmancard:seed
```

Создаются:

| Уровень | Названия | Количество |
|---|---|---|
| Корень | `Тестовая организация 1` … `Тестовая организация 5` | 5 |
| Дочерние | `Подразделение N.1` … `Подразделение N.3` | 15 |

`divcode` формируется автоматически моделью `Model_Restmancard_Org` — с префиксом
`dv_` и транслитерацией названия: `dv_testovaya_organizaciya_1`,
`dv_podrazdelenie_1.1`. Это тот же код, который сформировала бы форма добавления
с включённым чекбоксом «Автоматически».

Параметры задачи:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--count` | `5` | количество корневых организаций (1–100) |
| `--children` | `3` | количество дочерних у каждой корневой (0–100) |
| `--dry-run` | `0` | `1` — только показать план, ничего не создавать |
| `--encoding` | `auto` | кодировка вывода: `auto`, `utf8`, `cp866`, `cp1251` |

Примеры:

```
... --task=restmancard:seed --dry-run=1
... --task=restmancard:seed --count=2 --children=1
... --task=restmancard:seed --encoding=cp866
```

Задача идемпотентна: организации с такими же названием и родителем
пропускаются, поэтому повторный запуск не создаёт дубликатов. Перед чтением
списка и перед проверкой результата сбрасывается кеш `restmancard_orgs_v2`.
Код возврата `1` — при ошибке входных данных, ошибке API или если проверка
структуры не прошла.

Справка по задаче: `... --task=restmancard:seed --help`. После запуска
организации видны на странице `restmancard/index` (при необходимости нажмите
«Обновить»).

## Тестовые сотрудники (задачи `restmancard:people:seed` и `restmancard:people:delete`)

Для проверки добавления сотрудников в модуле есть две Minion-задачи. Они
работают только через REST API v2 и не обращаются к Firebird напрямую.

### Задача 1 — добавить по 3 сотрудника в каждую организацию

`restmancard:people:seed` читает все организации и для каждой создаёт трёх
сотрудников. `tabnum` формируется как `<prefix>_<ID_ORG>_<N>`; при префиксе по
умолчанию `test` получаются `test_4_1`, `test_4_2`, `test_4_3`.

Запуск:

```
c:\xampp\php\php.exe c:\xampp\htdocs\city\modules\minion\minion --task=restmancard:people:seed
```

Что делает задача:

1. `GET /api/v2/organizations` — все организации (все страницы).
2. `GET /api/v2/Person/GetList` — существующие сотрудники.
3. Для каждого ожидаемого `tabnum`:
   * если сотрудника нет — `POST /api/v2/Person` (`tabnum`, `surname`,
     `name`, `patronymic`);
   * затем `PATCH /api/v2/Person` с `tabnum` и `id_org` — привязка к
     организации.
4. Если `PATCH` не удался, только что созданный сотрудник удаляется
   (`DELETE /api/v2/Person`), чтобы повторный запуск не пропустил его.
5. Если сотрудник уже существует, задача не создаёт дубликат, но повторно
   отправляет `PATCH id_org` — это восстанавливает привязку после прерванного
   запуска.
6. В конце список сотрудников перечитывается и проверяется, что все ожидаемые
   `tabnum` на месте.

Способы запуска:

```
:: по 3 сотрудника в каждую организацию (по умолчанию)
... --task=restmancard:people:seed

:: по 5 сотрудников
... --task=restmancard:people:seed --count=5

:: только показать план, ничего не создавать
... --task=restmancard:people:seed --dry-run=1

:: другой префикс tabnum
... --task=restmancard:people:seed --prefix=qa

:: кодировка консоли
... --task=restmancard:people:seed --encoding=cp866

:: справка
... --task=restmancard:people:seed --help
```

Параметры:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--count` | `3` | сотрудников на каждую организацию (1–50) |
| `--prefix` | `test` | префикс `tabnum` (латиница, цифры, `-`, `_`, `.`) |
| `--dry-run` | `0` | `1` — только показать план |
| `--encoding` | `auto` | кодировка вывода: `auto`, `utf8`, `cp866`, `cp1251` |

Имена тестовых сотрудников: фамилия `Тестов`, имя `Сотрудник`, отчество
`Организация <ID_ORG>`.

### Задача 2 — удалить всех тестовых сотрудников

`restmancard:people:delete` читает всех сотрудников, отбирает те, чей `tabnum`
начинается с префикса (по умолчанию `test`, сравнение без учёта регистра), и
удаляет каждого через `DELETE /api/v2/Person?tabnum=...`. Вместе с сотрудником
API удаляет его идентификаторы (карты).

Запуск:

```
c:\xampp\php\php.exe c:\xampp\htdocs\city\modules\minion\minion --task=restmancard:people:delete
```

Способы запуска:

```
:: сначала посмотреть список, ничего не удаляя
... --task=restmancard:people:delete --dry-run=1

:: удалить всех с префиксом test (по умолчанию)
... --task=restmancard:people:delete

:: другой префикс
... --task=restmancard:people:delete --prefix=qa

:: кодировка консоли
... --task=restmancard:people:delete --encoding=cp866

:: справка
... --task=restmancard:people:delete --help
```

Параметры:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--prefix` | `test` | префикс `tabnum`; пустой запрещён |
| `--dry-run` | `0` | `1` — только показать список |
| `--encoding` | `auto` | кодировка вывода: `auto`, `utf8`, `cp866`, `cp1251` |

Задача не удаляет сотрудников с другими `tabnum` (например, `tn_SysAdmin`).
Если список сотрудников обрезан настройкой `people.max_pages`, задача
завершается до удаления, чтобы не оставить часть тестовых сотрудников; в этом
случае увеличьте `people.max_pages` и повторите запуск. Ответ `404` при
удалении считается уже выполненным удалением и не является ошибкой.

### Проверка результата

После `restmancard:people:seed` в каждой организации должно быть по 3
сотрудника. Проверить распределение по `ID_ORG` можно запросом к Firebird:

```sql
SELECT ID_ORG, COUNT(*)
FROM PEOPLE
WHERE TABNUM LIKE 'test%'
GROUP BY ID_ORG
ORDER BY ID_ORG;
```

После `restmancard:people:delete` запрос должен вернуть 0 строк. Страница
`restmancard/index` показывает `test_<ID_ORG>_<N>` в ветке соответствующей
организации: например, `test_4_1`, `test_4_2`, `test_4_3` видны у организации
с `ID_ORG = 4`. Привязка читается из Firebird (см. раздел «Сотрудники в
ветках организаций»), поэтому распределение на странице совпадает с запросом
выше.

## Как устроено чтение

1. `Model_Restmancard_Api` получает JWT через `GET /login?username=...&pasword=...`
   (имя параметра пароля в сервисе — `pasword`), кеширует токен в файловом кеше
   Kohana и повторяет запрос один раз после ответа `401`.
2. `Model_Restmancard_Org` читает **все** страницы `GET /api/v2/organizations`
   и строит дерево локально по полю `parent` (это `divcode` родителя). Так на
   сотни организаций уходит несколько HTTP-запросов, а не запрос на каждый узел.
3. `Model_Restmancard_People` читает `GET /api/v2/Person/GetList` и
   `GET /api/v2/Identifier/GetList`, сопоставляя карты по `tabnum`, а
   `getOrganizationMap()` читает из Firebird карту `TABNUM -> ID_ORG`.
4. `Model_Restmancard_Org::getTree()` раскладывает сотрудников по узлам с
   подходящим `ID_ORG` (остальные — в `people_root_divcode`) и считает
   счётчики организации и поддерева.
5. `Controller_Restmancard::action_index()` собирает дерево, готовит JSON для
   панели «Свойства» и рендерит `views/restmancard/index.php`.

## Ограничения контракта v2

* `GET /api/v2/Person/GetList` возвращает только `tabnum`, `surname`, `name`,
  `patronymic` — **организация сотрудника в ответе не передаётся** (ID_ORG есть
  только во входных данных `PATCH /api/v2/Person`), а фильтры по организации
  сервис игнорирует. Модуль определяет организацию по Firebird
  (`PEOPLE.ID_ORG`) и показывает сотрудника в ветке этой организации. Если
  Firebird недоступен или `people.org_map = false`, сотрудники показываются у
  `people_root_divcode` (по умолчанию `dv_All`). `POST /api/v2/Person` создаёт
  сотрудника с `ID_ORG = 1`, а форма добавления и Minion-задачи перепривязывают
  его к нужной организации через `PATCH`.
* У организации в ответе нет счётчиков сотрудников/подразделений: числа в
  бейджах считаются по локально построенному дереву.
* Списки сотрудников и идентификаторов ограничены `max_pages`, чтобы страница
  не делала сотни запросов. При обрезке выводится предупреждение; задача
  `restmancard:people:delete` в этом случае отказывается удалять, чтобы не
  оставить часть тестовых сотрудников.
* В веб-интерфейсе реализованы добавление и удаление организаций
  (`POST` и `DELETE /api/v2/organizations`) и сотрудников (`POST`, `PATCH` и
  `DELETE /api/v2/Person`). Редактирования реквизитов сотрудника, перемещения
  между организациями, массовых операций, изменения/перемещения организаций и
  категорий доступа (`PATCH/PUT /api/v2/organizations`,
  `POST /api/v2/Person/AddAccess` и др.) в этой версии нет.
* `POST /api/v2/Person` не принимает организацию: сотрудник создаётся с
  `ID_ORG = 1`, и только затем `PATCH` переставляет его в выбранную
  организацию. Если `PATCH` не удался, модуль удаляет созданного сотрудника.
* API не удаляет организацию каскадно: при наличии дочерних подразделений или
  активных сотрудников возвращается `409`, поэтому их нужно удалить или
  переместить заранее.
* В swagger поле `divcode` помечено nullable, но фактически сервис требует его
  при создании: без кода — `400 VALIDATION_ERROR`. Поэтому модуль всегда
  отправляет `divcode`: ручной из формы либо сформированный автоматически
  (см. раздел «Чекбокс «Автоматически» у поля divcode»).
* Формат автоматического кода задаёт модуль (`dv_` + транслитерация названия),
  а не API. Если в организации принят другой шаблон `divcode` (например,
  числовой `ID_ORG`, как в `mancard`), выключите чекбокс «Автоматически» и
  введите код вручную либо измените `organizations.divcode_prefix` и
  `Model_Restmancard_Org::_divcode_slug()/generateDivcode()`.

## Отличия от mancard

* Основной источник данных — REST API v2; Firebird используется только для
  чтения карты `TABNUM -> ID_ORG` (привязка сотрудников к веткам организаций).
* Модальные окна добавления и удаления организаций и сотрудников;
  редактирования, массового перемещения и сохранения категорий доступа нет.
* Форма добавления сотрудника спрашивает только фамилию (в `mancard` обязательны
  фамилия и имя), а `tabnum` умеет формировать REST API.
* Дата-время выводится как ISO-время API в UTC (`dd.mm.yyyy hh:mm UTC`).
* Кодировка ответов API — UTF-8; из Firebird читаются только `TABNUM` и
  `ID_ORG`, `TABNUM` перекодируется в UTF-8 (в `mancard` перекодируются все
  строки модели).

## Диагностика

Если страница показывает «REST API недоступен»:

1. Проверьте, что сервис отвечает:
   `curl http://localhost:5056/swagger/v2/swagger.json`
2. Проверьте логин:
   `curl "http://localhost:5056/login?username=ADMIN&pasword=333"`
3. Проверьте логи Kohana: `application/logs/`.
4. Сбросьте кеш кнопкой «Обновить» или удалите файлы
   `application/cache/restmancard_*`.

Если сотрудники показаны не в своих организациях:

1. Проверьте, что `people.org_map` включён, а инстанс `people.org_map_db`
   (`fb`) есть в `application/config/database.php`.
2. Проверьте привязку в Firebird:
   ```sql
   SELECT TABNUM, ID_ORG, "ACTIVE"
   FROM PEOPLE
   WHERE TABNUM = 'test_4_1';
   ```
   `ID_ORG` должен совпадать с полем `id` организации в
   `GET /api/v2/organizations`.
3. Убедитесь, что `ID_DB` сотрудника равен `people.org_map_id_db` (по
   умолчанию `1`).
4. Сбросьте кеш: ключ `restmancard_people_org` или кнопка «Обновить».

Если добавленный сотрудник не появился в ветке организации:

1. Проверьте привязку в Firebird по его `tabnum`:
   ```sql
   SELECT TABNUM, ID_ORG, ID_DB
   FROM PEOPLE
   WHERE TABNUM = '<tabnum>';
   ```
   Если строки нет или `ID_ORG` не тот, значит `PATCH` не выполнился: форма в
   этом случае должна была вернуть ошибку и удалить созданного сотрудника.
2. Проверьте, что организация есть в списке `GET /api/v2/organizations`:
   сотрудник раскладывается по узлу с совпадающим `id`.
3. Нажмите «Обновить»: карта `TABNUM -> ID_ORG` кешируется на
   `people.org_map_cache_lifetime` секунд.
